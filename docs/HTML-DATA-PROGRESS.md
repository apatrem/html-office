| Bench gate | Fixed on `fix/data-main-thread-gate`, in review | `warmCalculationMainTaskUnder100MS` (`packages/data/bench/browser.mjs`) failed at random on GitHub runners (PR #72, docs only, 182 ms; PR #68 185 then 106 ms; #61 102 ms) on code that cannot affect it. The CI CPU profiles show why: the gate took the single longest task over five warm edits, and that task was mostly main-thread garbage collection, either a collection left over from the cold open (123 ms, as the warm window opens) or a major collection inside one edit (160–370 ms), plus an occasional slow edit on a slow runner. The gate now forces a collection before the warm window (`HeapProfiler.collectGarbage`), gives each long task to the edit that started before it ended (tasks ending before the first warm edit count for none), takes each edit's longest task, and requires the **median over the five edits** to be under 100 ms. The budget is unchanged. Recalculation work runs on every edit, so a real regression raises every edit and fails every run. A pause in only one or two edits of five no longer fails the gate; `mainThreadMaxMS` still reports the single longest task. Locally (Apple M5) the median was 0 ms over 10 runs (idle, 8 and 10 busy cores), 53–65 ms at 4× CPU throttling and 96–105 ms at 6× throttling with 8 busy cores, where our own work reaches the budget. A deliberate 150 ms loop in the edit path gave medians of 157–168 ms and failed every run (5 of 5 on 100k×8, plus P&L, idle and loaded). |
