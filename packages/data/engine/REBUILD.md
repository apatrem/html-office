# Typed IronCalc build

Upstream: IronCalc v0.9.0, commit `297553dc3a37ec6b0f4821055220e3d26c4ac6a1` (MIT OR Apache-2.0). `typed-binding.rs` replaces the broad upstream UI binding with the narrow API needed by this prototype, including a WASM `getCellValue(sheet,row,column)` method returning `[kind,value]` through the existing public raw getter plus the error type. No formatted numeric strings are parsed. The original typed.1 artifact intentionally retained upstream calculation semantics. Since html-office.3 the build also applies the explicit formula compatibility patch described below; html-office.4 adds the TEXT rounding correction. Dates remain numeric serials at the engine boundary.

Developer prerequisites: Rust 1.95.0 with `wasm32-unknown-unknown`, wasm-bindgen-cli 0.2.126, Python 3, Git and the repository's locked npm dependencies (`npm ci`; `npm ci --prefix packages/data`). These are authoring/build tools, never installations triggered by a generated document.

`bash packages/data/engine/rebuild.sh <temporary-source-directory>` checks out the pinned upstream commit, applies the dependency/formula-compatibility patches and copies the narrow binding, builds with the committed Cargo lock, runs the pinned JS bundler and Binaryen optimiser, and regenerates the dependency audit/notices. Review binary hashes after rebuilding; an executable change requires a new manifest/version and regenerated workbooks. The custom binary is distributed with this repository, not represented as the upstream npm artifact.

The target-specific audit records the normal/build Cargo packages, including host proc macros conservatively. The `xlsx` feature and Python/Node bindings are excluded. All declared licences in this closure are permissive. Complete retained licence/notice texts live in `THIRD-PARTY-NOTICES.txt`, which stays exactly as `audit.py` writes it so `--check` can compare it. Both HTML modes embed them through `tools/notices.mjs` and the shared generator `packages/shared/notices.mjs` (task L01): each distinct licence text is stored once, after the packages and copyright holders it covers, with no wording dropped. Rust 1.95.0 standard-library notices are retained conservatively for all targets, with identical full texts deduplicated. The compiler/optimiser themselves are development tools; runtime standard-library/compiler builtins notices are included.

`bitcode_derive` 0.6.9 omits its licence text from the published crate. Its `.cargo_vcs_info.json` identifies upstream commit `f41da053c08178189aaee8c62f4c6e738add6eda`; `license-sources/bitcode_derive-LICENSE-MIT` is retained from that exact revision at https://raw.githubusercontent.com/SoftbearStudios/bitcode/f41da053c08178189aaee8c62f4c6e738add6eda/LICENSE-MIT . The audit rejects missing texts or an unreviewed licence expression.

The surrounding Office code remains MIT. Third-party components retain their own terms. Audit scope is this exact build/feature/target closure; a dependency, toolchain or feature change requires a new audit.

## Rebuild verification and transport

Rebuild output goes into the temporary checkout's `office-artifacts/`, leaving approved artifacts untouched. Pass `--check` as the second argument to compare JavaScript, raw WASM and notices against the repository. Source/cache paths are remapped before compilation. On 19 October 2026, two independent checkout paths produced identical JavaScript, optimised WASM and notices. The raw WASM SHA-256 is recorded in `manifest.json` and verified in tests.

`tools/pack-engine.mjs` creates a deterministic gzip transport with Node's level-9 zlib. The manifest pins compressed and decoded hashes separately. Transport compression bytes can depend on the Node/zlib version; a new compressed representation requires its own recorded digest even when the decoded engine is identical. `record-engine.mjs` must run after committing the artifact files so URLs refer to an immutable revision that actually contains them.

The current custom build is 2,172,743 decoded WASM bytes and 707,874 gzip bytes, plus a 7,381-byte JavaScript wrapper. A fresh real HTTPS/file:// smoke confirmed the compressed asset was requested only on the first edit and passed both checks. These are measurements of this prototype, separate from the earlier upstream npm/Brotli measurement. See `bench/cdn-results.json` for the response sizes and environment.

## Formula compatibility build (T12)

`formula-compatibility.patch` remains on the same pinned upstream source and fixes range-shape checking in plural criteria functions, typed criteria-error propagation, single-criterion sum/average alignment (including a single-cell reference), AND/OR evaluation of later errors, XLOOKUP single-cell references, and TEXTJOIN empty-string handling. Lifted SUMIF criteria preserve individual errors without discarding successful sibling results. This is a distinct custom IronCalc version, `ironcalc/0.9.0+html-office.3`, with no secondary evaluator or new dependency. The committed 89-case aggregation/logic fixture stores independent hand-derived expected values with reference provenance; it is not an exhaustive Excel conformance claim. See [ADR-006](../../../docs/decisions/006-formula-compatibility-patches.md).

On 20 October 2026 two fresh checkouts at different paths produced identical JavaScript, raw/gzip WASM and notices. The candidate has 2,175,542 raw WASM bytes, 709,786 gzip bytes and the unchanged 7,381-byte JS wrapper. The audit still contains 38 target packages, 47 notice texts and 197,573 notice bytes, with byte-identical notices. The provenance header explicitly identifies the intentional formula compatibility corrections; upstream licence texts are unchanged. The patched native upstream suite passed 2,768 tests with eight existing upstream ignores; the added regression covers the changed semantics. Both distributions, full suites, real HTTPS delivery and independent source/artifact/notice reviews passed. The integrated pin passed all five unchanged CI performance gates in run 39438492098 before PR #25 merged.

## TEXT rounding build (html-office.4)

The T21 acceptance workbook found that TEXT rounded exact binary halves to even: `TEXT(2.5,"0")` gave "2", `TEXT(0.125,"0%")` "12%" and `TEXT(1234.5,"#,##0")` "1,234", while `ROUND(2.5,0)` already gave 3. Upstream's number formatter rounded through Rust's float formatting, which is ties-to-even. The same path printed `TEXT(-1,"0")` as "1" and `TEXT(0.999,"0.00")` as "0.00". `formula-compatibility.patch` now rounds non-scientific number formats like ROUND: the value is read at 15 significant digits, then rounded half away from zero at the format's decimals, so `TEXT(2.675,"0.00")` gives "2.68" and `TEXT(-2.5,"0")` gives "-3". Formats whose decimals already cover the value's 15 significant digits (leading zeros after the point do not count), and scientific formats, keep the previous path, so `TEXT(-5E-15,"0.00000000000000")` gives "-0.00000000000001". Negative zero is unchanged: `TEXT(-0.4,"0")` still gives "0". The new version is `ironcalc/0.9.0+html-office.4`; workbooks saved by html-office.3 show their results as stale until recalculated.

The lookup/text/number fixture gains 12 hand-derived tie cases (81 in all). On 29 October 2026 a rebuild of html-office.3 on the same machine first matched its committed bytes and notices (`--check`). Two fresh checkouts at different paths then produced identical html-office.4 JavaScript, raw/gzip WASM and notices: 2,175,074 raw WASM bytes, 709,700 gzip bytes, and the unchanged 7,381-byte wrapper, notices and dependency audit. The patched native upstream suite passed 2,770 tests (two new) with the same eight upstream ignores.
