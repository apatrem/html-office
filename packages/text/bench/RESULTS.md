Raw results, every run included: [`results-m5.json`](results-m5.json) (local), [`results-m5-throttle-6.json`](results-m5-throttle-6.json) (local, CPU slowed six times), [`results-ci-chromium.json`](results-ci-chromium.json) and [`results-ci-engines.json`](results-ci-engines.json) (GitHub runners, PR #102, commit `1e1f34f`). ## Method

- **Runs**: per engine and document, one warm-up run (discarded), then five runs, each in a fresh browser context of the same browser (no draft from an earlier run). Tables give the median and, in brackets, the range of the five. Viewport 1280×900; any request beyond `file://` is refused and counted (none was made).
- **Open**: navigation start to the first frame painted after the editor is ready (`window.htmlText` set).
- **Keystroke-to-paint**: from the key event's timestamp to the end of the next rendered frame (a message posted from `requestAnimationFrame`), one key at a time, 21 characters typed at the end of the middle paragraph. *Median* is each run's median keystroke; *worst* is each run's slowest keystroke. Frames come every 16.7 ms, so a keystroke costs up to one frame of waiting even when no work is done.
- **Editing operations**: Enter, Backspace, Bold on a word, Heading 2 (renumbering and the contents), a new footnote (renumbering the notes) and two undos, 600 ms apart. Input-to-paint for each; in Chromium also the longest main-thread task overlapping it (Long Tasks API, which reports tasks of 50 ms and over: "< 50" means none). Long tasks between operations (the draft written to the browser's storage 500 ms after an edit) are reported as *background*. Chromium collects garbage before the editing window (as Data's gate, PR #73). Firefox and WebKit have no Long Tasks API: their input-to-paint bounds the task from above.
- **Save**: File › Save a copy, the whole synchronous save (serialise, read back with DOMParser, write the blob) to the next paint; the downloaded copy is validated and must hold the edits.
- **Print preview**: the command to the next paint. **PDF**: Playwright's `page.pdf` in Chromium (Firefox and WebKit cannot print to PDF under Playwright; `tests/print-firefox.mjs` prints in stock Firefox without timing).
- **Memory**: Chromium's JS heap after a forced collection, after the edits; the browser process tree's peak resident memory, sampled every 200 ms with `ps` (shared pages counted more than once, short peaks may be missed). Neither is the tab's own footprint.

## Targets

The plan proposed, at 50 pages: **keystroke-to-paint under 50 ms** and **no editing task over 100 ms**.

- **Validated** on the measured documents, machines and engines: the slowest keystroke of a run stays at or under 30 ms (median of runs) in every engine on CI and 19 ms locally; no Chromium editing operation or background draft write has a task of 50 ms or more; the slowest editing operation paints within 28 ms (WebKit, CI). With the CPU slowed six times the 50-page document still meets both (41 ms, no long task), at the edge in one run of five (55.6 ms).
- They are kept unchanged as the CI gate: `--check` fails when, at 50 pages, the median over five runs of each run's slowest keystroke reaches 50 ms (every engine) or the median of each run's longest editing task reaches 100 ms (Chromium). At 100 pages, a stress document, the limits are 100 ms and 200 ms: they catch a regression without promising the 50-page targets there, although the measurements meet them too.
- **Regression check**: a temporary 150 ms busy loop in the editor's `dispatchTransaction` (removed, never committed) made the gate fail: Chromium keystroke worst 158 ms and longest editing task 158–161 ms, WebKit keystroke worst 163 ms, all against the 50-page limits; the command exited with status 1.

Not covered by these targets: open, save, print preview and PDF are one-off commands. On CI, the slowest is WebKit's print preview of the 100-page document (0.9 s); every median open is under 0.6 s (the slowest single open, 0.63 s, is Firefox's at 100 pages).

## Findings

- **Fixed** (`editor/commands.mjs`): after every edit the shell asks each style and list command whether it applies, and each walked the whole document for its textblocks. The walk is now cached per document (documents never change). A CPU profile of one run's editing window on the 100-page document at six-fold throttling put 147 ms of the 424 ms spent dispatching transactions in these checks before the change; at that throttle, the slowest keystroke went from 49.5 to 41.1 ms at 50 pages and from 61.9 to 53.4 ms at 100 pages, where the only long task (56 ms) disappeared.
- **Remaining, listed**: each transaction still walks the whole document a few times (the editing guards' repeated-ID, link and table-shape checks, and the list commands' dry run in their enabled check): about 2 ms a keystroke at six-fold throttling on 100 pages, under 0.5 ms unthrottled. Not worth changing at these sizes; they grow linearly with the document.
- **Memory**: Chromium's JS heap is 5–6 MB for both documents after a collection; the DOM and layout live outside it. The browser trees' RSS (130–950 MB, by engine and machine) is mostly the browser itself and grows by 1–76 MB from 50 to 100 pages.
